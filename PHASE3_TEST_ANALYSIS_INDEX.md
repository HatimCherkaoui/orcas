## 🏗️ Architecture Context

### Orchestration Flow (for test understanding)
```
1. Workflow launched via @LaunchWorkflow or WorkflowEngine.start()
   ↓
2. JdbcWorkflowStateStore persists initial state (workflow, context, metadata rows)
   ↓
3. WorkflowEngine routes to first step, publishes StatusEvent to Kafka
   ↓
4. KafkaWorkflowEventPublisher sends event to Kafka topic
   ↓
5. WorkflowEventConsumer receives message from Kafka topic
   ↓
6. Engine.handle(StatusEvent) evaluates StatusCriteria, routes to next step(s)
   ↓
7. JdbcWorkflowStateStore.record() updates step/workflow status, writes audit logs
   ↓
8. Workflow completes (SUCCESS/FAILED), JdbcWorkflowStateStore.finish() marks terminal state
   ↓
9. Dashboard queries via WorkflowServiceController → JdbcWorkflowQueryService
   ↓
10. Operators replay via WorkflowServiceController → JdbcWorkflowAdminService
```

### Concurrency Model (for test scenarios)
- Parallel steps may execute concurrently (tested via `Executors.newVirtualThreadPerTaskExecutor()`)
- JdbcTransactionRunner auto-retries on database deadlock/serialization failure
- Circuit breaker can short-circuit flaky calls, triggering WorkflowRetryScheduler
- Retry scheduler batches replays via ScheduledExecutorService

## 📞 Analysis Questions & Answers

**Q: Why no @Mock/@InjectMocks?**
A: Project prefers inline anonymous interface implementations over annotation-based mocking. This aligns with manual dependency injection philosophy in framework-agnostic core module.

**Q: Why use Testcontainers instead of H2/embedded DB?**
A: PostgreSQL-specific SQL (TIMESTAMP WITH TIME ZONE) and audit trail design requires real relational semantics. Example-app integration test already proven this pattern.

**Q: How do we test concurrent state store operations?**
A: Simulate concurrent workflow step execution via multiple threads calling store.record() simultaneously. JdbcTransactionRunner should retry on deadlock.

**Q: Should integration tests use @SpringBootTest?**
A: Yes, but only for service controller, query service, and admin service. JDBC state store and Kafka consumer tests can use lighter containers without full Spring context if needed.

**Q: What about test fixtures?**
A: Consider creating helper classes (WorkflowFixture, StatusEventFixture) to reduce boilerplate, especially for service controller tests with many endpoints.
